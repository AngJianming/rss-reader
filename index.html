    CVE-2026-119618: Apache HTTP/2 Pre-Auth RCE — What the Race Condition Actually Does
    There is a CVSS 9.8 pre-authentication remote code execution vulnerability in Apache HTTP Server’s mod_http2 module. It was fixed on 11 November 2026 in version 2.4.71. If you run Apache with HTTP/2 enabled and you have not patched, this post is for you. What happens mod_http2 is designed so that worker threads never touch the connection’s shared allocator — each worker gets a private one. assign_headers() breaks that rule for a specific request shape: body-less, with Content-Type and no Content-Length, when the request header table is full. The worker writes a synthesised Content-Length: 0 into the shared stream table. That write races with the connection thread on a lock-free free list. Two threads pop the same node. Heap corrupts. The process ends up with double-owned memory, and that’s the primitive the exploit turns into code execution. No credentials. No user interaction. The attacker sends an HTTP/2 request. Who’s affected Apache HTTP Server 2.4.55 through 2.4.70, and standalone mod_h2 2.0.8 through 2.0.42 — but only if HTTP/2 is enabled. That’s the h2 or h2c token in the Protocols directive. The directive can be set server-wide or per virtual host, so check both. Scale Wiz reports 64% of cloud environments have resources on a vulnerable version, and 51% have publicly exposed instances. A containerised differential lab, ThreadSanitizer evidence, and a stdlib HTTP/2 PoC are already on GitHub under the CVE identifier. Fix Upgrade to Apache HTTP Server 2.4.71 or mod_h2 2.0.43. If you can’t patch today: Protocols http/1.1 in every config file and every virtual host block.     You Watched Five People Try Your Feature and Most of Them Could Not Find It
    Your team finally ran a usability session. Five people from outside the team were asked to complete a task using the new feature you built, while you watched quietly on a call. Three of them never found the button. One found it and then did not trust what it did. Only one finished without help. You spent six weeks on that feature. Watching it fail in silence is one of the hardest kinds of feedback to receive, because nobody is saying anything critical. They are just struggling, and you cannot help. That is exactly why it is so valuable. Every other kind of feedback on your work is somebody's opinion. This is behaviour. Nobody was being polite, nobody was guessing what users might do, and nobody had read the design document first. Resist the first reaction, which is to explain. They should have looked at the menu. They were not our target users. The tooltip covers it. Some of that may be true, but if three people out of five missed it, the next three hundred will as well. The usability researcher Jakob Nielsen has long argued that a handful of test users finds most of the obvious problems, which is why five people can tell you so much. Instead, go back through the recordings or your notes and write down the exact moments people hesitated. Where did their mouse go first? What did they say out loud while they looked? Which words on the screen did they read, and which did they skip? Those moments are your list of fixes, and they are far more precise than anything a reviewer could have written. Then separate the problems from the solutions. Users are excellent at showing you where something is wrong and much less reliable at telling you how to fix it. If one participant says just make the button red, note that they could not see it, and then decide with your designer how to make it findable. Finally, thank the team for running the session, and ask to watch the next one before you build anything. The cheapest time to learn this lesson is before six weeks of work. – Asael Shinder  ( 6 min )
