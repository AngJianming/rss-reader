    GeoServer probing: distinguishing exposure from confirmed compromise
    WatchTowr observed probing of two GeoServer vulnerabilities that appeared aimed at finding vulnerable servers. However, it had not reported successful remote code execution by attackers. Organizations operating GeoServer need to distinguish Internet exposure, vulnerable software and evidence of compromise when assessing their systems. Eye Security identified Internet-accessible servers, but that finding does not establish how many are vulnerable or compromised. TMGS emphasizes that asset inventory, vulnerability remediation and incident investigation each require their own evidence. According to SecurityWeek, the two vulnerabilities being probed belong to a chain of five flaws discovered by Rapid7 researcher Jonah Burgess. Combined with other flaws, they can lead to unauthenticated remote code execution. This does not establish that either vulnerability independently allows an attacker to take over a server. GeoServer has released patches. TMGS recommends upgrading to 3.0.2, 2.28.6 or 2.27.7. The absence of reported successful code execution is not a reason to delay remediation while probing is already being observed. TMGS recommends inventorying GeoServer deployments, recording their actual versions and Internet accessibility, and assigning someone to verify each upgrade. Prioritize Internet-accessible systems and restrict access according to business needs while updates are pending. For outsourced deployments, TMGS recommends obtaining the post-update version and functional test results from the responsible provider. Completion should include a confirmed version and a working service after the update.     I built a Telegram alert relay that never sees portfolio data
    I built a Telegram alert relay that never sees portfolio data FolioSpan is a local-first portfolio tracker. When users asked for Telegram delivery of price alerts, the obvious design — send the portfolio to a server, evaluate there, forward the alert — was off the table. The app's whole point is that holdings never leave the device unless you opt in. So the relay is deliberately blind. Alert evaluation happens on-device. The app periodically checks prices in the background and composes the finished notification text locally — "Portfolio value crossed 1.00", "BTC moved -6.2% in 24h". The worker is a dumb pipe. A Cloudflare Worker exposes /link, /webhook, /send, /status. Its KV stores only an opaque link token mapped to a chat ID. No holdings, no prices, no portfolio — ever. Linking is one-shot. The app opens a t.me/bot?start= URL; the token is single-use with a 10-minute TTL. /stop in Telegram wipes the binding from KV, and the app clears its local credentials on the next status check. The message travels verbatim. The client posts the finished text to /send; the worker relays it to Telegram HTML-escaped, capped at 3,500 chars and 60 messages/day. If the relay is compromised tomorrow, the attacker gets a table of random tokens and chat IDs — not a single holding. The privacy contract isn't "we promise not to look"; it's that there is nothing to look at. No two-way bot. /stop is the only command; anything else gets a help message. Query commands like /portfolio would require the server to see holdings — a different product, not a toggle. Local-time semantics. Quiet hours and the daily fire cap are enforced by the on-device policy engine before a message is ever produced — the relay doesn't need to know about them.
