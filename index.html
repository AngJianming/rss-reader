    Three CSV rows can mean one company: check the row unit before deduplicating
    A CSV with 10,000 rows does not necessarily describe 10,000 companies. Before comparing datasets—or deduplicating one—write down what one row represents. Consider this fictional sample: entity_id,location_id,price_usd example-a,site-1,20 example-a,site-1,20 example-a,site-2,30 It has three rows, one distinct entity and two distinct entity/location pairs. The repeated pair needs investigation. It might be an accidental duplicate, or the export might be missing an observation date that distinguishes two legitimate records. Ask whether a row represents an entity, a location, an offer or an observation at a particular time. A useful key could be (entity_id, location_id, observed_at) rather than just entity_id. Test the proposed key against your sample before trusting a join or a coverage claim. from collections import Counter keys = [(r['entity_id'], r['location_id']) for r in rows] repeated = {key: n for key, n in Counter(keys).items() if n > 1} This identifies repeated keys; it does not decide which rows to delete. Keep the original file, investigate differences and define a resolution rule first. Blindly keeping the first row can discard a newer observation or a different product. If both sides contain repeated join keys, a merge can multiply rows. A larger output is not automatically broader coverage. Check key uniqueness on each side and compare expected versus actual row counts after joining. My dataset-buyer checklist includes a linked fictional fixture and an executable count check. Use small, inspectable examples to settle the meaning of a row before processing the whole file.
