With 83k events, it turns a page load into a coffee break. Nothing was broken in the usual sense. The code was correct. It was just doing far more work than it needed to, on every request. The fix wasn't clever. Instead of scanning all the events on each page load, the dashboard now counts visitors from an in-memory index. That one change took the load time from 177 seconds to 13 ms. A fix like this is easy to undo by accident. Someone adds a feature, a query creeps back toward a full scan, and nobody notices until a user does. So I added a benchmark to CI. If the dashboard gets meaningfully slower, the build tells me before anyone else finds out. This all happened in the middle of a week with three releases: payment sync for Stripe, Dodo, Polar and LemonSqueezy, a read API, and an MCP server. It would have been easy to skip the slow page and keep shipping features. I'm glad I didn't. Test with real-sized data early. A hundred rows would never have shown me the 177 seconds. The problem only appeared once the data looked like something a real user might have, and by then it was cheap to fix because I caught it before anyone relied on it.
